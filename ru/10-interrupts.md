# 12. Прерывания и джиттеринг

Прерывания — тема, которую в мануалах по Aleste и CPC
объясняют плохо. Между тем, без понимания прерываний
невозможно написать нормальную программу, которая
синхронизируется с экраном: музыку, анимацию, игру,
демо.

В этом разделе — как работают прерывания в CPC и Aleste,
почему они «дрожат» (джиттер), и как с этим бороться.

## Откуда берутся прерывания

В CPC и Aleste прерывания генерирует не процессор и не
внешнее устройство, а **Gate Array** — та же микросхема,
которая управляет палитрой, режимами экрана и банкингом.

Внутри Gate Array есть **6-битный счётчик**, который
инкрементируется на каждом сигнале HSYNC (горизонтальная
синхронизация). Каждая строка экрана — это один HSYNC.

Счётчик считает до 52, потом сбрасывается в 0. Поскольку
кадр состоит из 312 HSYNC (стандартный PAL-кадр), за
один кадр счётчик успевает досчитать до 52 шесть раз.

Когда счётчик достигает значения 52 — генерируется
прерывание. То есть **за один кадр может быть до шести
прерываний**.

## Как работает сброс счётчика

Есть два способа сбросить счётчик.

**Первый:** бит 4 регистра RMR (Gate Array, регистр 2).
Когда этот бит установлен, счётчик HSYNC сбрасывается.
Это программный сброс.

**Второй:** сигнал VSYNC (вертикальная синхронизация).
Когда Gate Array «чувствует» VSYNC, счётчик тоже
сбрасывается. Это аппаратный сброс, происходит
автоматически в начале каждого кадра.

После сброса по VSYNC проверяется: если 6-й бит счётчика
был равен 0 (то есть счётчик был меньше 32), прерывание
генерируется. Если счётчик был больше или равен 32 —
прерывание не генерируется.

На практике это значит: **если прерывание не было
обработано (не сброшено процессором), то при следующем
VSYNC счётчик уже досчитал до 52, и новое прерывание
не будет сгенерировано**. Это защита от накопления
необработанных прерываний.

## Проблема: джиттер

Вот тут начинается самое интересное.

Прерывание генерируется **не в момент VSYNC**, а через
два HSYNC после него. Это ~128 микросекунд задержки.

Кроме того, момент, когда процессор реально получит
прерывание, зависит от того, что он делал в этот момент.
Если процессор выполняет длинную инструкцию — прерывание
подождёт. Если короткую — обработается быстрее.

Это называется **джиттер** — дрожание момента прерывания
относительно экрана. Для музыки и анимации это критично:
если обработчик прерывания запускается в разные моменты
кадра, эффект будет нестабильным.

## Решение: синхронизация через HALT

Чтобы получить точную синхронизацию с экраном, используют
комбинацию polling + HALT.

Идея такая:

1. Программа опрашивает бит VSYNC в порту B PPI (`#F5XX`),
   пока он не станет активным.
2. Как только VSYNC обнаружен — выполняется инструкция
   `HALT`. Процессор останавливается и ждёт прерывания.
3. Прерывание приходит через два HSYNC после VSYNC.
   Процессор просыпается точно в этот момент.

Пример на ассемблере:

```
; Синхронизация с началом кадра
LD B, #F5          ; порт B PPI

vsync_loop:
    IN A, (C)      ; читаем порт B
    RRA            ; бит 0 в carry (VSYNC)
    JR NC, vsync_loop  ; ждём, пока VSYNC станет активным

    HALT           ; засыпаем до прерывания
    ; ... просыпаемся синхронно с экраном
```

Почему это работает: код опроса VSYNC имеет **переменную
задержку** в конце (зависит от того, на какой итерации
цикла мы поймали VSYNC). Если бы мы не использовали HALT,
момент пробуждения был бы неточным. HALT «съедает» эту
неопределённость: процессор засыпает и просыпается
строго по сигналу прерывания, независимо от того, где
он был в цикле.

## Сколько спит процессор

После HALT процессор просыпается через **~128 микросекунд**
плюс время, потраченное в обработчике прерывания.

128 микросекунд — это два HSYNC. Именно столько проходит
от VSYNC до момента генерации прерывания.

Это значит: **если тебе нужно что-то сделать точно
в начале кадра, у тебя есть 128 микросекунд форы**.
Или наоборот — ты должен учитывать эту задержку.

## Практический пример: счётчик кадров

Классическая задача — считать кадры. Вот как это делается
с синхронизацией через HALT.

```
FrameCounter: DB 0

; В обработчике прерывания
InterruptHandler:
    PUSH AF
    PUSH BC
    PUSH DE
    PUSH HL

    ; Увеличиваем счётчик кадров
    LD HL, FrameCounter
    INC (HL)

    ; ... тут код, который должен выполняться
    ;     раз в кадр (музыка, анимация)

    POP HL
    POP DE
    POP BC
    POP AF
    EI
    RETI

; Основная программа
MainLoop:
    ; Синхронизация
    LD B, #F5
sync:
    IN A, (C)
    RRA
    JR NC, sync
    HALT

    ; Теперь мы синхронны с кадром
    ; Можно делать что-то, что займёт меньше кадра
    ; ...

    JR MainLoop
```

Обрати внимание: обработчик прерывания должен сохранять
все регистры, которые использует, и завершаться `EI` +
`RETI`.

## Альтернатива: программная задержка

Иногда вместо HALT используют программную задержку —
пустой цикл, который занимает ровно столько времени,
сколько нужно. Это работает, но менее надёжно: если
прерывание случится во время задержки, она сдвинется.

HALT надёжнее, потому что процессор буквально
останавливается и ждёт сигнала.

## Что это значит для программиста

**Прерывания в CPC/Aleste — это 50 Гц.** Шесть
прерываний за кадр, но реально используется одно —
то, которое приходит после VSYNC.

**Джиттер — враг.** Если делаешь музыку или анимацию,
синхронизируйся через HALT, а не через polling.

**128 микросекунд — твоя фора.** Учитывай её, если
нужна точность.

**Обработчик должен быть коротким.** Чем дольше он
работает, тем больше вероятность, что следующее
прерывание будет пропущено.

**Сброс счётчика — через RMR.** Если по какой-то
причине прерывание не обрабатывается и счётчик
переполнен, сбрось его через бит 4 регистра RMR
Gate Array.
